REVIEW

Review protocol

How to review a published gap, close it with an official source and request the change — including what a change request has to contain.

Why this page exists. The site publishes gaps on purpose, so a reviewer can close them after the site is live. This page says exactly how: which source closes which flag, and what a change request must contain.
01 / PROTOCOL

Review and change-request protocol

Five steps, no manual data entry.

StepWhat to doReference
1 · Read the flagOpen the flagged item and its official source link. The link is the starting point for investigation, not a certificate that the answer is there.Reference ↗ ↗
2 · Check the registerLook for the matching question in the questions register. A flag without a registered question is a new item that should be added.Reference ↗ ↗
3 · Choose a pathMark a suggestion as accept, defer or reject with a reason. Implementation starts only after that mark exists.Reference ↗ ↗
4 · Record the decisionOpen a change request on the repository with the flag ID, the source that closes it and the expected effect on the affected tables.Reference ↗ ↗
5 · Re-verifyThe next deployment re-captures the official sources and re-runs the verification. The flag stays published until the evidence supports closing it.Reference ↗ ↗
02 / WHAT TO INCLUDE

Checklist for a change request

Short and specific beats long and vague.

REQUIRED

Four things

  • The flag or suggestion id, for example F-02 or SI-04.
  • The official source that establishes the value, with its URL.
  • The capture or observation time, so the value can be reproduced.
  • The table or page the change affects.
REJECTED

What does not close an item

  • A secondary report of an official fact, with no primary link.
  • A value inferred from another value, for example a replacement derived from a roster list.
  • A community dataset described as official data.
  • A request to fill a blank cell without a source.
